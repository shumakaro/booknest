# Лабораторная работа 10 Full Stack и тестирование

## 1 Тема и цель
Клиент React соединён с собственным FastAPI и PostgreSQL. Цель работы — выполнить пользовательские сценарии без заглушек, согласовать данные формы с сервером, централизовать ошибки и защитить критические пути тестами. Отчёт включает лекцию, практику и СРС недели 13.

## 2 Программное обеспечение
Использованы существующий React 19, TypeScript 6, Vite 8, FastAPI, PostgreSQL 17 и pytest. Для клиентских проверок установлены Vitest 5.1.0, React Testing Library, user-event, jest-dom и jsdom; для сквозного сценария — Playwright 1.65.0. Точные версии сохранены в package-lock.json. Браузерные проверки локально выполнены через Edge.

## 3 Краткая теория
По лекции 13 воспроизводимость означает отсутствие машинных настроек в прикладном коде. Клиент обращается по относительному /api/v1, Vite проксирует запросы на адрес из окружения. Единый формат code/message/details/request_id позволяет обрабатывать ошибки в одном месте. Интеграционные тесты проверяют HTTP, данные и бизнес-правило, клиентские — доступное поведение формы, e2e — весь путь через браузер.

## 4 Ход выполнения
Создана зависимая ветка lab-10/fullstack. Поиск и детали переключены с Open Library на API BookNest. Идентификатор сервера преобразуется в строку для сохранения прежних компонентов. Каталог получает данные даже при пустом запросе; поиск, жанр, доступность, сортировка и страница сохраняются в URL, а фильтрация выполняется на сервере.

Существующая форма сохранена и подключена к реальной записи. Ранее часть полей при редактировании подставлялась заглушками. Новая ревизия 004 добавила publisher, edition_year и pages; язык уже существовал. Для старых демонстрационных записей год издания заполнен исходным годом, неизвестное издательство обозначено явно. Межполевая проверка года выполняется Pydantic и ограничением БД. При PATCH учитывается сохранённое состояние; изменение первой публикации выше года издания требует передать согласованный год издания.

Корректный ISBN-10 старой формы переводится в ISBN-13 с проверкой контрольных цифр; ISBN-13 дополнительно проверяется сервером. Автор ищется через API и при отсутствии создаётся; конфликт одновременного создания обрабатывается повторным поиском. Ошибки полей сервера переводятся в прежние имена полей формы.

Добавлены выдача в деталях и возврат в разделе выдач. Ревизия 005 создала персональное серверное желаемое. Изменения списка показываются оптимистично, а при ошибке предыдущее состояние восстанавливается. Старые утилиты и файлы предыдущих работ сохранены; источник действующего каталога полностью собственный.

## 5 Объяснение файлов
api/client.ts добавляет токен, выполняет одну попытку refresh, передаёт request_id и формирует понятные сообщения. Исправлена ошибка: неудача повторного запроса после успешного refresh больше не считается ошибкой самого обновления и не завершает сеанс при 422.

api/books.ts переводит собственные BookRead в прежние Book и BookDetails. api/bookForm.ts преобразует поля формы и ISBN. api/wishlist.ts выполняет настоящие персональные запросы без искусственной задержки. BooksPage показывает загрузку, пустой список, результат и ошибку с повтором; BookDetailsPage, LoansPage и WishlistPage обрабатывают те же состояния.

ErrorBoundary показывает понятный экран при ошибке отрисовки. app/core/http.py сохраняет одинаковый request_id в ответе 500 и журнале, не раскрывая внутреннюю причину. tests/conftest.py выдаёт отдельную сессию на booknest_test с внешним откатом и проверяет ревизию до запуска миграций.

## 12 Дополнительные вопросы лабораторной
Отдельного списка вопросов нет; следующие вопросы составлены для защиты.

Почему год издания проверяется повторно при PATCH? Запрос может передать только год публикации, поэтому схема должна видеть и сохранённый год издания. Полное согласованное состояние проверяется Pydantic, но репозиторию передаются только действительно изменяемые поля.

Почему после 422 не выполняется logout? Ошибка валидации не означает недействительный сеанс. Обновление могло успешно завершиться; его ошибка и ошибка повторного действия разделены.

Почему e2e не удаляет исходный каталог? Сценарий запоминает идентификатор только что созданной книги и изменяет только её. Удаление мягкое, поэтому история выдачи сохраняется.

## 13 Дополнительные вопросы практики
Как доказана изоляция тестов? Тестовая БД отдельная, результаты откатываются внешней транзакцией, повторные прогоны зелёные. Почему компонент ищется по label? Это проверяет доступное имя и не зависит от оформления CSS. Как воспроизведён красный тест без сброса проекта? Код прошлой ветки прочитан git show в отдельный игнорируемый файл и подключён только отдельной конфигурацией Vitest.
