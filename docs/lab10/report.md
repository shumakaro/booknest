# Лабораторная работа 10 Full Stack и тестирование

## 1 Тема и цель
Клиент React соединён с собственным FastAPI и PostgreSQL. Цель работы — выполнить пользовательские сценарии без заглушек, согласовать данные формы с сервером, централизовать ошибки и защитить критические пути тестами. Отчёт включает лекцию, практику и СРС недели 13.

## 2 Программное обеспечение
Использованы существующий React 19, TypeScript 6, Vite 8, FastAPI, PostgreSQL 17 и pytest. Для клиентских проверок установлены Vitest 5.1.0, React Testing Library, user-event, jest-dom и jsdom; для сквозного сценария — Playwright 1.65.0. Точные версии сохранены в package-lock.json. Браузерные проверки локально выполнены через Edge.

## 3 Краткая теория
По лекции 13 воспроизводимость означает отсутствие машинных настроек в прикладном коде. Клиент обращается по относительному /api/v1, Vite проксирует запросы на адрес из окружения. Единый формат code/message/details/request_id позволяет обрабатывать ошибки в одном месте. Интеграционные тесты проверяют HTTP, данные и бизнес-правило, клиентские — доступное поведение формы, e2e — весь путь через браузер.

## 11 Контрольные вопросы лекции 13
### Лекция 13
### Три способа соединить клиент и сервер в разработке — в чём различие и что выбрать?
Можно разрешить отдельный origin через CORS, использовать dev-proxy Vite или поставить общий reverse proxy. В разработке proxy даёт относительные запросы и один origin в браузере. В эксплуатации Nginx раздаёт SPA и проксирует API; CORS нужен только для действительно разрешённых внешних клиентов.

### Какие значения обязаны быть переменными окружения и почему?
Адрес БД, ключ подписи, сроки токенов, origins и адрес dev-proxy зависят от среды и задаются окружением. Иначе перенос потребует правок исходного кода и создаст риск публикации секретов. В Git сохраняется .env.example с описанием полей, а реальные значения находятся вне репозитория.

### Почему VITE_API_KEY нельзя считать секретом?
Переменные VITE_ подставляются в клиентский JavaScript при сборке. Любой пользователь может получить этот код и прочитать значение. Поэтому ключи сервера не передаются клиенту даже под именем API_KEY; в браузер попадает только общедоступная конфигурация.

### Из каких полей должен состоять единый формат ошибки API?
Единый конверт содержит code, message, details и request_id. code служит машинной обработке, message объясняет действие пользователю, details уточняет поля или причины, request_id связывает ответ с журналом. Все обработчики используют один формат, а чувствительные входные значения в него не включаются.

### Что допустимо сообщить клиенту при ошибке 500, а что — только записать в лог?
Клиенту сообщается нейтральное описание сбоя и request_id для обращения за помощью. Трассировка, SQL, адреса внутренних узлов и другие технические подробности остаются в серверном журнале. Даже лог не должен содержать пароль, Authorization или refresh-токен.

### Зачем нужен request_id и как им пользоваться при разборе инцидента?
request_id связывает действия одного запроса между ответом и журналом. Пользователь передаёт идентификатор, а разработчик находит соответствующую запись и трассировку. В BookNest UUID создаётся сервером, включается в конверт ошибки и X-Request-ID; время обработки записывается рядом.

### Что такое пирамида тестирования и почему интеграционных тестов API в учебном проекте больше всего?
Пирамида различает быстрые узкие unit-тесты, более широкие интеграционные проверки и немного дорогих e2e-сценариев. В небольшом учебном API интеграционный тест дёшево проверяет сразу HTTP-контракт, валидацию, зависимости и бизнес-правило. Поэтому основной критический набор здесь составляют API-тесты, дополненные проверками компонентов и одним сквозным сценарием.

### Как обеспечить независимость тестов друг от друга?
Каждый тест получает собственные данные, определённые фикстурами, и не зависит от порядка запуска. Используется отдельная БД с внешней транзакцией и откатом; commit приложения помещается в savepoint. Счётчики, cookies, токены и подмены зависимостей также должны очищаться или создаваться заново.

### Зачем подменять зависимость get_db в тестах?
Подмена направляет маршруты в тестовую сессию и позволяет откатить все изменения после проверки. Без неё приложение может обратиться к рабочему engine, даже если тест подготовил отдельную БД. В FastAPI используется dependency_overrides, который очищается после теста.

### Почему в React Testing Library элементы ищут по роли и метке, а не по классу?
Роль и доступное имя соответствуют тому, как пользователь и вспомогательные технологии находят элемент. Такой тест переживает смену CSS-класса и одновременно проверяет доступность интерфейса. Проверять следует поведение: ввод, сообщение об ошибке, отправку и результат, а не внутреннюю структуру разметки.


## 12 Дополнительные вопросы лабораторной
Отдельного списка вопросов нет; следующие вопросы составлены для защиты.

Почему год издания проверяется повторно при PATCH? Запрос может передать только год публикации, поэтому схема должна видеть и сохранённый год издания. Полное согласованное состояние проверяется Pydantic, но репозиторию передаются только действительно изменяемые поля.

Почему после 422 не выполняется logout? Ошибка валидации не означает недействительный сеанс. Обновление могло успешно завершиться; его ошибка и ошибка повторного действия разделены.

Почему e2e не удаляет исходный каталог? Сценарий запоминает идентификатор только что созданной книги и изменяет только её. Удаление мягкое, поэтому история выдачи сохраняется.

## 13 Дополнительные вопросы практики

Это проверяет доступное имя и не зависит от оформления CSS. Как воспроизведён красный тест без сброса проекта?
