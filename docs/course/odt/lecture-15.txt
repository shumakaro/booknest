[1433] Лекция 15 · Неделя 15
[1434] Code review, оптимизация и профессиональная траектория
[1435] 2 ч
[1436] Learning objectives
[1437] Провести структурированное code review чужого проекта и сформулировать замечания конструктивно.
[1438] Измерить производительность приложения и определить приоритет оптимизаций по данным, а не по интуиции.
[1439] Оценить собственное решение: назвать сильные стороны, ограничения и обоснованные альтернативы.
[1440] Составить план дальнейшего профессионального развития с опорой на пройденный стек.
[1441] Основные понятия
[1442] code review, конструктивная обратная связь, читаемость кода, технический долг, метрики Lighthouse (LCP, CLS, TBT), размер бандла, code splitting, ленивая загрузка, кэширование, индексы как оптимизация, профилирование запросов, наблюдаемость, портфолио, техническое интервью, SSR и Next.js (обзор), WebSocket, очереди задач, кэш Redis, Kubernetes, мониторинг
[1443] План лекции
[1444] 1. 0–20 мин. Code review: зачем он существует, что именно проверяется (корректность, читаемость, безопасность, соответствие договорённостям), как формулировать замечание («этот запрос выполнится N+1 раз» вместо «плохой код»), различие блокирующих замечаний и предложений.
[1445] 2. 20–40 мин. Разбор двух анонимизированных проектов прошлого потока: сильные и слабые места, разбор по официальной рубрике.
[1446] 3. 40–62 мин. Оптимизация по измерению: Lighthouse на своём приложении, размер бандла и rollup-plugin-visualizer, ленивая загрузка маршрутов, кэширующие заголовки; на backend — план запроса, индекс, устранение N+1, пагинация. Правило: сначала измерить, потом оптимизировать.
[1447] 4. 62–80 мин. Что осталось за пределами курса и в каком порядке это изучать: SSR и Next.js, серверное состояние (TanStack Query), управление состоянием, WebSocket, фоновые задачи и очереди, кэш, наблюдаемость, Kubernetes. Честная карта: что действительно требуется на первой работе, а что нет.
[1448] 5. 80–95 мин. Портфолио и трудоустройство: как оформить репозиторий проекта, что писать в README, как рассказывать о проекте на интервью, типичные вопросы junior-собеседования по темам курса.
[1449] 6. 95–110 мин. Организация защиты: регламент, состав комиссии, критерии, порядок демонстрации, ответы на вопросы.
[1450] Теоретический материал
[1451] Заключительная лекция переводит студента из режима «выполняю задание» в режим инженерной ответственности за решение. Ключевое умение — говорить о собственном коде критически: назвать, что сделано хорошо, что является техническим долгом и что было бы сделано иначе при наличии времени. На защите это оценивается напрямую: студент, который честно указывает на слабое место своего проекта и предлагает путь исправления, демонстрирует более высокий уровень, чем студент, утверждающий, что всё идеально.
[1452] Второй тезис — оптимизация без измерения бессмысленна. К этому моменту студенты уже владеют двумя инструментами измерения (Lighthouse и EXPLAIN ANALYZE), и лекция сводит их в единое правило: измерить, найти самое дорогое, исправить, измерить снова. Наиболее частая находка в учебных проектах — не медленный React, а отсутствующий индекс или N+1, что даёт хороший урок о соотношении усилий и эффекта. Третий тезис — карта дальнейшего пути. Курс сознательно не охватил многое, и об этом следует сказать прямо, указав порядок изучения и связь с пройденным материалом: TanStack Query — как развитие собственных хуков недели 7; SSR — как ответ на ограничения SPA недели 1; очереди — как ответ на долгие операции недели 13.
[1453] Практические примеры
[1454] Lighthouse на реальном студенческом проекте до и после трёх правок (сжатие изображений, ленивая загрузка маршрутов, кэширующие заголовки).
[1455] Один индекс, ускоряющий главную страницу проекта в 30 раз — с планами запроса до и после.
[1456] Разбор трёх формулировок одного замечания: обидная, бесполезная и конструктивная.
[1457] Code examples
[1458] Ленивая загрузка маршрутов: меньше кода в первой загрузке
[1459] // было: все страницы в одном бандле — 780 КБ
[1460] import { AdminPage } from "./pages/AdminPage";
[1461]
[1462] // стало: страница администратора догружается только тем, кто её открывает
[1463] import { lazy, Suspense } from "react";
[1464] const AdminPage = lazy(() => import("./pages/AdminPage"));
[1465]
[1466] <Route path="admin" element={
[1467]   <Suspense fallback={<Spinner label="Загрузка раздела" />}>
[1468]     <AdminPage />
[1469]   </Suspense>
[1470] } />
[1471] // первичный бандл: 780 КБ → 310 КБ
[1472] Шаблон конструктивного замечания на code review
[1473] # Плохо (оценка личности, без содержания)
[1474] "Тут всё написано ужасно, перепиши."
[1475]
[1476] # Бесполезно (нет ни причины, ни пути исправления)
[1477] "Не оптимально."
[1478]
[1479] # Конструктивно: место → следствие → предложение → приоритет
[1480] "app/repositories/books.py:34 — связь `author` загружается лениво,
[1481] поэтому список из 20 книг даёт 21 запрос в БД (виден в логе при echo=True).
[1482] Предлагаю добавить `.options(selectinload(Book.author))`.
[1483] Приоритет: блокирующее — на 500 книгах страница не откроется."
[1484] Демонстрация на занятии
[1485] «Ревью в прямом эфире». Преподаватель открывает Pull Request одного из студентов (с его согласия) и проводит ревью по рубрике вслух: сначала запускает проект по README (проверка воспроизводимости), затем смотрит структуру, затем три случайных файла, затем целенаправленно проверяет пять пунктов безопасности, затем оставляет 5–7 комментариев разного приоритета. Демонстрация показывает не только как проверять, но и как выглядит проект со стороны — это сильнейшая мотивация привести собственный репозиторий в порядок перед защитой.
[1486] Типичные ошибки студентов
[1487] Замечания в форме личной оценки вместо описания технического следствия.
[1488] Оптимизация «на глаз» без единого измерения; переписывание React-компонентов при отсутствующем индексе в БД.
[1489] README на две строки: проект невозможно запустить, и защита начинается с неудачи.
[1490] Демонстрация проекта с локальной машины «на всякий случай» при неработающем публичном адресе.
[1491] Ответ «я не знаю, это из интернета» на вопрос о собственном коде.
[1492] Утверждение, что в проекте нет недостатков.
[1493] Все коммиты сделаны в последние два дня семестра.

[1504] Домашнее задание
[1505] Финальная подготовка к защите: (1) провести code review проекта закреплённого однокурсника по официальной рубрике — не менее 8 содержательных комментариев в PR, из них минимум 2 по безопасности; (2) устранить замечания, полученные от рецензента; (3) привести в порядок README (описание, стек, схема БД, инструкция запуска, скриншоты, публичный адрес, декларация использования AI); (4) подготовить демонстрационный сценарий на 7 минут и один слайд с архитектурной схемой; (5) заполнить самооценку по рубрике итогового проекта из раздела 15.
