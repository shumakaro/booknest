# Лабораторная работа 12 Подготовка развертывания BookNest

## 1 Тема и цель
Подготовлен перенос BookNest на VPS за Nginx с HTTPS. Отчет охватывает недели 14 и 15. Конфигурация и эксплуатационные процедуры созданы, но публичное развертывание не выполнено: домен и VPS не предоставлены. Этот статус не заменяется демонстрацией localhost.

## 2 Программное обеспечение
Использованы FastAPI, PostgreSQL 17, React, Docker Compose, Nginx, Certbot и GitHub Actions. Для локальных измерений использованы Lighthouse 13.6.0 и Edge. Docker Engine локально отсутствует; реальные контейнерные проверки выполняются на GitHub runner.

## 3 Краткая теория
Обратный прокси завершает TLS и передает запрос приложению. Сертификат подтверждает доменное имя, поэтому пример домена в конфигурации не является действительным публичным адресом. Резервное копирование считается проверенным после восстановления в отдельную базу и сравнения данных. Миграции применяются последовательно и сохраняют историю схемы.

## 4 Ход выполнения
Ветка lab-12/deployment продолжает lab-11/docker. Созданы шаблоны первоначального HTTP и окончательного HTTPS Nginx, production override Compose и пример переменных. Внешний Nginx получает сертификат через webroot, перенаправляет HTTP на HTTPS, включает HSTS, CSP и запрет определения MIME по содержимому. API и PostgreSQL не публикуются наружу. Внутренний web привязан к loopback.

Установлены точные границы доверия прокси. Uvicorn принимает forwarded-заголовки только от фиксированного внутреннего IP web, а не от произвольного источника. Host Nginx перезаписывает адрес клиента. Подготовлена проверка поддельных заголовков против ограничения входа.

Скрипт обновления отказывается работать при измененных файлах, делает backup и использует только fast-forward либо явно выбранный тег. Скрипт восстановления требует нового имени с суффиксом _restore_test и отказывается перезаписывать существующую базу. Проверяются контрольная сумма и количества основных строк. Системный таймер ежедневной копии подготовлен, но не установлен на несуществующем VPS.

## 11 Контрольные вопросы лекций 14 и 15
### Лекция 14
### Чем контейнер отличается от виртуальной машины?
Контейнер запускает изолированные процессы с использованием ядра хоста; виртуальная машина включает отдельную гостевую ОС и ядро. Поэтому контейнер обычно легче и быстрее запускается. Linux-контейнеры на Windows всё равно требуют совместимой среды, часто виртуальной машины через WSL2.

### Почему COPY requirements.txt должен идти до COPY .?
Сначала копируется редко меняющийся список зависимостей и выполняется установка, затем исходный код. Тогда правка Python-файла не отменяет кэш слоя установки пакетов. Если сначала выполнить COPY . ., любое изменение проекта заставит пересобрать все последующие слои.

### Что даёт multi-stage сборка и на сколько уменьшает образ клиента?
Multi-stage оставляет в конечном образе только результат сборки и необходимые runtime-файлы. Node, компилятор и node_modules сборщика не переходят в Nginx-образ. Лекция приводит пример примерно 1,2 ГБ → 50 МБ; собственный размер нужно измерить docker images, а не выдавать пример лекции за результат проекта.

### Как сервис api находит базу данных внутри compose-сети?
Compose создаёт сеть и внутренний DNS по именам сервисов. Поэтому адрес БД для api — db:5432, а localhost внутри api указывает на сам контейнер. Публикация порта БД на хост для общения сервисов не требуется.

### Зачем нужен том и что произойдёт при docker compose down -v?
Именованный том хранит данные независимо от жизненного цикла контейнера. Обычный down удаляет контейнеры и сеть, но сохраняет том; down -v удаляет и связанные тома, что уничтожает данные. На существующем проекте такая команда не выполняется без явного разрешения и необходимой резервной копии.

### Для чего нужен healthcheck и почему depends_on без него недостаточен?
Healthcheck проверяет готовность сервиса, например ответ pg_isready. Обычный depends_on задаёт порядок запуска контейнеров, но не означает готовность PostgreSQL принимать подключения. condition: service_healthy заставляет API дождаться успешной проверки.

### Объясните строку try_files $uri $uri/ /index.html.
Nginx сначала ищет файл по $uri, затем каталог по $uri/. Если ничего нет, отдаётся /index.html, после чего маршрут обрабатывает React Router. Это позволяет открыть /books/42 напрямую; для отсутствующего API-маршрута должен сохраняться серверный 404, а не HTML SPA.

### Что делает reverse proxy и почему API не публикуют напрямую?
Reverse proxy принимает внешний запрос и передаёт API на внутренний сервис. Это даёт единую точку TLS, ограничений, заголовков и журналов. Если API опубликован напрямую, часть этих правил можно обойти; поэтому снаружи открывается только web-вход.

### Как передать секреты в контейнер, не помещая их в образ?
Секреты передаются при запуске через окружение или механизм secrets, а не COPY и не Dockerfile ARG. Локальный .env исключается из Git и контекста сборки. Доступ к файлу сервера ограничивается; переменные клиента VITE_ для секретов не подходят.

### Как выполняется повторное развёртывание после изменений в коде и в схеме БД?
После получения нового кода собирается новая версия, проверяется резервная копия и применяются новые миграции перед стартом API. Затем проверяются health, журналы и основной сценарий. Откат приложения возможен только при совместимой схеме; удалять том для обновления нельзя.

### Что должно происходить в CI при каждом Pull Request?
При каждом PR выполняются установка зафиксированных зависимостей, линтер, backend-тесты на отдельной БД, клиентские тесты и production-сборка. Ошибка должна дать ненулевой код и красный статус. Автоматическое объединение и публикация секретов в лог недопустимы; деплой отделяется от проверки PR.

### Лекция 15
### Что проверяется при code review и в каком порядке?
Сначала проверяется воспроизводимость запуска по README, затем основной сценарий и обработка ошибок. Далее проверяются безопасность, связи и миграции, структура кода, тесты и документация. Замечания связываются с наблюдаемым результатом и официальной рубрикой, а не с предпочтениями рецензента.

### Как сформулировать замечание, чтобы оно было принято и исполнено?
Используется схема место → следствие → предложение → приоритет. Например: запрос автора в цикле создаёт N+1; предлагается selectinload и повторный подсчёт SELECT. Комментарий должен описывать код и проверяемое исправление, не оценивать личность автора.

### Что означают метрики LCP и TBT и как их улучшить?
LCP измеряет время появления крупнейшего видимого элемента содержимого. TBT в лабораторном Lighthouse суммирует блокирующие части длинных задач главного потока после FCP до интерактивности. Для улучшения проверяются доставка и размер основного ресурса, изображения, лишний JavaScript и длинные вычисления; изменения подтверждаются повторным одинаковым замером.

### Как определить, что тормозит приложение — клиент, сеть или БД?
Во вкладке Network сопоставляются ожидание сервера и передача ресурсов; в Performance исследуются задачи браузера. На сервере используются request_id и время обработки, а в БД — число запросов и EXPLAIN ANALYZE. Оптимизируется самый дорогой измеренный участок, затем замер повторяется.

### Что даёт code splitting и когда он оправдан?
Code splitting делит JavaScript на части, загружаемые при необходимости. Он полезен для тяжёлых редко открываемых маршрутов, например административной формы. Слишком мелкое разбиение увеличивает число запросов и сложность, поэтому решение оценивается по размеру первого бандла и времени загрузки.

### Какие ограничения имеет SPA и какую задачу решает SSR?
SPA может требовать загрузки JavaScript до появления полезного содержимого и сложнее обеспечивать SEO или быстрый первый показ. SSR формирует HTML на сервере и решает часть этих задач, после чего клиент может гидратировать страницу. Он добавляет серверную сложность и сам по себе не исправляет медленную БД.

### Назовите три недостатка собственного проекта и способы их устранения.
Для BookNest существенные ограничения — отсутствие подтверждённого публичного HTTPS-развёртывания, локальный ограничитель запросов для одного процесса и необходимость независимого ревью. Решения: предоставить VPS/домен и проверить runbook, использовать общее хранилище ограничителя при масштабировании, провести согласованное ревью с реальным участником. Непроверенные результаты не следует объявлять выполненными.

### Какую технологию за пределами курса вы изучите первой и почему?
Логичным следующим шагом является TanStack Query: он развивает уже написанные хуки загрузки и помогает с кэшем, повторной загрузкой и состоянием серверных данных. Для учебной работы собственные простые хуки полезны пониманием механизма. Выбор дальнейшей технологии следует связать с наблюдаемой проблемой проекта, а не только с популярностью.

### Что должно быть в README проекта, чтобы его смог запустить незнакомый разработчик?
Нужны назначение, стек и версии, схема данных, список переменных, точные команды запуска и тестов, миграции и наполнение. Также указываются Docker, обновление, резервное копирование, публичный адрес при его наличии, скриншоты и AI_USAGE. Инструкция проверяется на чистой среде без неописанных ручных правок.
