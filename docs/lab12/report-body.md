# Лабораторная работа 12 Подготовка развертывания BookNest

## 1 Тема и цель
Подготовлен перенос BookNest на VPS за Nginx с HTTPS. Отчет охватывает недели 14 и 15. Конфигурация и эксплуатационные процедуры созданы, но публичное развертывание не выполнено: домен и VPS не предоставлены. Этот статус не заменяется демонстрацией localhost.

## 2 Программное обеспечение
Использованы FastAPI, PostgreSQL 17, React, Docker Compose, Nginx, Certbot и GitHub Actions. Для локальных измерений использованы Lighthouse 13.6.0 и Edge. Docker Engine локально отсутствует; реальные контейнерные проверки выполняются на GitHub runner.

## 3 Краткая теория
Обратный прокси завершает TLS и передает запрос приложению. Сертификат подтверждает доменное имя, поэтому пример домена в конфигурации не является действительным публичным адресом. Резервное копирование считается проверенным после восстановления в отдельную базу и сравнения данных. Миграции применяются последовательно и сохраняют историю схемы.

## 4 Ход выполнения
Ветка lab-12/deployment продолжает lab-11/docker. Созданы шаблоны первоначального HTTP и окончательного HTTPS Nginx, production override Compose и пример переменных. Внешний Nginx получает сертификат через webroot, перенаправляет HTTP на HTTPS, включает HSTS, CSP и запрет определения MIME по содержимому. API и PostgreSQL не публикуются наружу. Внутренний web привязан к loopback.

Установлены точные границы доверия прокси. Uvicorn принимает forwarded-заголовки только от фиксированного внутреннего IP web, а не от произвольного источника. Host Nginx перезаписывает адрес клиента. Подготовлена проверка поддельных заголовков против ограничения входа.

Скрипт обновления отказывается работать при измененных файлах, делает backup и использует только fast-forward либо явно выбранный тег. Скрипт восстановления требует нового имени с суффиксом _restore_test и отказывается перезаписывать существующую базу. Проверяются контрольная сумма и количества основных строк. Системный таймер ежедневной копии подготовлен, но не установлен на несуществующем VPS.

## 5 Объяснение файлов
Документ docs/deployment.md содержит последовательность SSH, firewall, сертификата, запуска, обновления и диагностики. Каталог deployment содержит shell-скрипты, Nginx и systemd. tools/render_nginx.py проверяет входные параметры. Workflow deploy.yml требует ручного запуска, подтверждения, проверенного тега и закрепленного SSH host key. Секреты не включаются в Git. tools/verify_release.py запрещает деплой коммита без успешных checks и containers.

## 6 Дополнительные задания
Подготовлены ручной SSH deploy, ежедневный backup с явно включаемой ротацией, /health, заголовки безопасности, gzip и кэширование ассетов. Внешний uptime-сервис, сертификат и сканер заголовков остаются непроверенными. Lighthouse после исправления контраста показал Performance 93 и Accessibility 100 на локальной мобильной симуляции; это не измерение публичного сервера.

## 7 Реальные проверки
Основной и production Compose прошли config --quiet, shell-скрипты прошли bash -n. На предыдущем коммите ЛР 11 реально прошли 49 backend-тестов, четыре клиентских теста, сборка, контейнерный сценарий и Playwright: https://github.com/shumakaro/booknest/actions/runs/42224231074. Новый CI https://github.com/shumakaro/booknest/actions/runs/42236984907 для 92c16e5 завершился успешно: checks и containers. Backup восстановлен в новую БД с 30 книгами и 20 выдачами; повторное восстановление отклонено. Поддельные адреса дали 401 пять раз и затем 429. В контейнерном профиле прошли 49 тестов. Выдержки сохранены в ci-results.txt.

Исходный Lighthouse: Performance 100, Accessibility 95, Best Practices 96, LCP около 0,8 с. После изменения контраста: Performance 93, Accessibility 100, Best Practices 96, LCP 0,787 с, TBT 317,7 мс, CLS 0. Измерения сохранены в lighthouse-before.json и lighthouse-after.json. Улучшение скорости не заявляется: оценка производительности снизилась при отдельном запуске, хотя целевой порог 90 достигнут. Исправлена реальная ошибка контраста. Ленивая загрузка выделила страницы, но общий начальный граф включает общий клиентский chunk; размер единственного index.js не считается размером всей загрузки.

Дополнительно в новом namespace screen_benchmark_20261106 базы booknest_sql измерен полный запрос главного экрана: автор, агрегированные жанры, доступность и сортировка первой страницы из 500 000 книг и 100 000 выдач. До индекса title,id получено 686,755 мс, после 2,088 мс; возвращены те же 20 строк. Исходные public-таблицы сохранили 30 книг и 20 выдач. Планы сохранены в catalog-benchmark.json. Это отдельный SQL-эксперимент, а не замер скорости HTTP или production-нагрузки.

## 12 Дополнительные вопросы лабораторной
Почему нельзя восстанавливать поверх рабочей базы? Это может повредить текущие данные и создать конфликты; проверка выполняется в новой базе. Что подтверждает config? Только корректность модели Compose, а не наличие работающего сервера. Почему применяется отдельный SECRET_KEY? Ключ разработки не должен давать возможность выпускать production-токены.
