### L7-A01 Почему data в PATCH не содержит все поля формы

Авторский учебный вопрос из прежнего сборника

**Полный ответ.** PATCH передает только изменяемую часть ресурса. Pydantic хранит набор явно заданных полей, а model_dump(exclude_unset=True) исключает отсутствующие. Явный null отличается от пропуска: разрешение null определяется схемой. После объединения с текущей книгой сервис повторно проверяет межполевые ограничения, например год издания.

**Реализация.** В роутере payload преобразуется в словарь измененных полей. CatalogService.save объединяет изменения с текущей записью и проверяет итоговое состояние.

**Краткий ответ.** PATCH меняет часть записи. Отсутствующее поле остается прежним. Явный null проверяется отдельно по правилам схемы.

**Демонстрация.** На отдельной тестовой книге изменить только год через Swagger UI. Повторно прочитать книгу и сравнить название, автора и год.

**Типичная ошибка.** Ошибка: отправить все поля формы с пустыми значениями и затереть сохраненные данные.

### L7-A02 Почему повторный ISBN является конфликтом

Авторский учебный вопрос из прежнего сборника

**Полный ответ.** ISBN является идентификатором издания и в схеме ограничен уникальностью. Корректный по формату ISBN может уже принадлежать другой записи: это конфликт состояния, поэтому используется 409. Ошибка формата ISBN относится к 422. При конфликте БД транзакция откатывается, и клиент получает понятное сообщение вместо SQL или трассировки.

**Реализация.** Сервис преобразует IntegrityError в 409 после rollback. BookCreate.check_isbn проверяет формат еще до сохранения.

**Краткий ответ.** Повторный ISBN нарушает уникальность. Формат запроса при этом может быть верным. Поэтому возвращается 409, а неверный формат дает 422.

**Демонстрация.** В локальной тестовой среде создать книгу с валидным ISBN, затем повторить создание с тем же ISBN и проверить 409. Не использовать чужую рабочую запись.

**Типичная ошибка.** Ошибка: объявить ISBN уникальным только в интерфейсе, оставив возможность двух одновременных вставок.

### L7-A03 Как различаются 404 и пустой список

Авторский учебный вопрос из прежнего сборника

**Полный ответ.** Адрес коллекции существует даже тогда, когда фильтр ничего не нашел. Поэтому список возвращает 200, пустой items и total=0. Обращение к одному отсутствующему ресурсу возвращает 404. Успешное создание дает 201, а успешное удаление дает 204 без JSON-тела. Эти различия позволяют клиенту правильно выбрать состояние интерфейса.

**Реализация.** Роутер деталей обращается к CatalogService.read; отсутствие записи приводит к 404. Список формируется репозиторием в общем конверте Page.

**Краткий ответ.** Пустая коллекция остается корректным результатом поиска. У нее код 200 и пустой список. Код 404 означает отсутствие конкретной книги.

**Демонстрация.** Сравнить GET списка с заведомо отсутствующим поисковым словом и GET несуществующего числового ID. Проверить и код, и тело ответа.

**Типичная ошибка.** Ошибка: возвращать 404 для пустого результата фильтра или JSON-тело при 204.

### L7-A04 Почему пример хранилища в памяти не подходит для Render

Авторский учебный вопрос из прежнего сборника

**Полный ответ.** Словарь в памяти удобен в ЛР7 для проверки контракта без настройки СУБД. Его содержимое теряется при остановке процесса, а несколько процессов получают разные словари. В интегрированном приложении данные хранятся в PostgreSQL, поэтому переживают перезапуск Render. **Демонстрация.** Показать MemoryStore и текущий роутер БД рядом. Не перезапускать production ради демонстрации потери данных.

**Типичная ошибка.** Ошибка: считать временный диск контейнера или память процесса надежным хранилищем.

### L7-A05 Как связываются ошибка клиента и журнал сервера

Авторский учебный вопрос из прежнего сборника

**Полный ответ.** Middleware назначает запросу UUID, измеряет длительность и добавляет X-Request-ID. Централизованный обработчик ошибок включает тот же идентификатор в конверт ответа. В журнал пишутся метод, путь, код и время, а внутреннее исключение остается на сервере. При обращении пользователя идентификатор помогает найти событие без передачи пароля, JWT или строки подключения.

**Реализация.** Вложенная trace создает request_id и пишет журнал; error_response возвращает его клиенту. Обработчик валидации не включает исходные значения полей.

**Краткий ответ.** Каждому запросу назначается идентификатор. Он связывает ответ с записью журнала. Пользователь получает понятную ошибку без внутренней трассировки.

**Демонстрация.** В локальной среде вызвать безопасный GET с несуществующим ID. Сравнить X-Request-ID, поле request_id и запись серверного журнала.

**Типичная ошибка.** Ошибка: выводить целиком тело запроса с паролем или возвращать текст SQL-исключения.

### L8-A01 Почему SQL и ORM не являются двумя разными базами

Авторский учебный вопрос из прежнего сборника

**Полный ответ.** DDL описывает таблицы, типы, ключи и ограничения напрямую на SQL. ORM описывает те же сущности классами Python и формирует SQL при выполнении операций. Это два представления структуры, а не две рабочие базы. Alembic хранит последовательность изменений схемы. В BookNest связи Author-Book являются 1:N, User-Profile являются 1:1, Book-Genre являются M:N через book_genres.

**Реализация.** Модели сопоставлены с db/schema.sql, результат сравнения сохранен в docs/lab8/orm-sql-comparison.md. Схема прикладного запуска создается миграциями.

**Краткий ответ.** SQL и ORM работают с одной реляционной схемой. ORM связывает таблицы с объектами Python. Изменение структуры фиксируется отдельной ревизией Alembic.

**Демонстрация.** Открыть db/er.mmd, db/schema.sql и app/models.py. Для Book показать внешний ключ автора и таблицу связи жанров.

**Типичная ошибка.** Ошибка: менять уже примененную миграцию или вызывать create_all вместо истории миграций.

### L8-A02 Как исключена двойная выдача последнего экземпляра

Авторский учебный вопрос из прежнего сборника

**Полный ответ.** Выдача состоит из чтения книги, проверки активных выдач и создания новой записи. Раздельное выполнение этих действий позволило бы двум запросам одновременно увидеть последний свободный экземпляр. Поэтому сервис берет блокировку строки книги FOR UPDATE и выполняет проверку и запись в одной транзакции. После commit следующий запрос видит новое состояние; при отсутствии экземпляров возвращается 409.

**Реализация.** CatalogRepository.get_book(lock=True) применяет with_for_update. Сервис проверяет доступность и повторную активную выдачу пользователю, затем выполняет один commit.

**Краткий ответ.** Проверка и создание выдачи выполняются вместе. Блокировка строки не дает одновременно выдать последний экземпляр. Проигравший запрос получает конфликт 409.

**Демонстрация.** В отдельной тестовой базе подготовить книгу с одним экземпляром. Показать тест конкурентной выдачи и убедиться, что активная выдача только одна.

**Типичная ошибка.** Ошибка: посчитать остаток до транзакции, а вставить выдачу позднее без блокировки.

### L8-A03 Почему индекс не гарантирует ускорение любого запроса

Авторский учебный вопрос из прежнего сборника

**Полный ответ.** Индекс ускоряет подходящие условия поиска, соединения или сортировки, но увеличивает затраты записи и занимает место. Планировщик сравнивает стоимость разных способов чтения. На маленькой таблице последовательное чтение может быть выгоднее. Для доказательства сравнивают один и тот же запрос, данные, фактическое время и число прочитанных строк в EXPLAIN ANALYZE до и после. Само наличие CREATE INDEX не доказывает ускорение.

**Реализация.** SQL-стенд содержит сравнение планов. Основные запросы и обоснование структуры находятся в db/queries.sql и db/README.md.

**Краткий ответ.** Индекс полезен только подходящему запросу. Планировщик может выбрать последовательное чтение небольшой таблицы. Ускорение подтверждается сопоставимыми планами EXPLAIN ANALYZE.

**Демонстрация.** Показать сохраненные планы и исходный запрос. Новый EXPLAIN ANALYZE выполнять только на отдельном стенде: он действительно исполняет запрос.

**Типичная ошибка.** Ошибка: сравнивать разные наборы данных или говорить об ускорении по одному имени индекса.

### L8-A04 Почему 30 книг не ограничивают поиск

Авторский учебный вопрос из прежнего сборника

**Полный ответ.** Учебные 30 книг описывают начальное наполнение, а не предел каталога. Репозиторий применяет фильтры к полному набору активных записей БД, затем считает total и выбирает страницу через OFFSET и LIMIT. ORDER BY с дополнительным Book.id делает порядок стабильным. Непоследовательное применение фильтров к total и items привело бы к неверному числу страниц.

**Краткий ответ.** В базе может быть больше 30 книг. Поиск выполняется до пагинации по всем подходящим записям. total показывает число совпадений, items содержит одну страницу.

**Демонстрация.** Показать тест поиска записи за первой страницей и запросы page=1, page=2 с одинаковыми фильтрами. Не добавлять записи в Neon ради кадра.

**Типичная ошибка.** Ошибка: сначала получить 30 книг, затем искать только в массиве браузера.

### L8-A05 Зачем нужны разные подключения Neon

Авторский учебный вопрос из прежнего сборника

**Полный ответ.** Приложению нужны короткие обычные запросы, для которых подходит pooled-подключение Neon. Инструменты миграций и резервного копирования используют прямое подключение с предсказуемым поведением сессии. Оба варианта ведут к одному проекту и ветке БД, но имеют разные свойства соединения. URL задаются в окружении, а не в исходниках. Для внешней БД требуется защищенный транспорт.

**Реализация.** Settings передает database_url в SQLAlchemy. Отдельный миграционный адрес обрабатывает migrations/env.py, а защищенную копию выполняет tools/backup_neon.py.

**Краткий ответ.** Pooled-подключение обслуживает обычные запросы приложения. Для миграций и dump используется прямой адрес. Оба адреса с паролем хранятся только вне Git.

**Демонстрация.** Показать имена переменных в .env.example и создание Session без вывода настоящего .env. Пароль и строку подключения не открывать на защите.

### L9-A02 Почему JWT нельзя исправить заменой роли в payload

Авторский учебный вопрос из прежнего сборника

**Полный ответ.** JWT содержит подписанные claims, но обычный подписанный JWT не шифрует их. Изменение role или sub нарушает подпись HS256. Сервер ограничивает алгоритм, проверяет срок, обязательные поля и тип токена. После декодирования он читает пользователя и его действующую роль из БД, проверяет активность и отзыв. Подпись не заменяет проверку прав на отдельный ресурс.

**Реализация.** decode_token допускает заданный состав claims; get_current_user проверяет пользователя и denylist. require_role использует роль загруженного пользователя.

**Краткий ответ.** Payload можно прочитать, поэтому секреты туда не помещаются. Подделка роли ломает подпись. Дополнительно сервер проверяет актуального пользователя и его права.

**Демонстрация.** Показать состав payload из кода и тест поврежденной подписи. Настоящий токен не вставлять в сторонний онлайн-декодер.

**Типичная ошибка.** Ошибка: доверять декодированному payload без проверки подписи или выбирать алгоритм из самого токена.

Код: app/core/security.py:41 decode_token

### L9-A03 Зачем logout при коротком access

Авторский учебный вопрос из прежнего сборника

**Полный ответ.** JWT до истечения exp остается криптографически действительным. Удаление токена из интерфейса само по себе не отзывает украденную копию. При выходе сервер сохраняет хеш отзываемых токенов в denylist и удаляет refresh-cookie. При последующих обращениях проверяется наличие отзыва. Истекшие записи можно очищать, поскольку истекший JWT и без них не принимается.

**Реализация.** Сервис сохраняет отзыв через AuthRepository. get_current_user и refresh проверяют отозванные токены; роутер удаляет cookie.

**Краткий ответ.** Выход должен завершать сессию и на сервере. Поэтому токены заносятся в список отозванных. Повторное обращение с прежним токеном отклоняется.

Для собственного VPS первые диагностические команды: docker compose ps, docker compose logs --tail=100 api web, curl -i https://<домен>/health. **Краткий ответ.** Сначала проверяется доступность /health и API. Затем сопоставляются версия деплоя и журналы сервиса. Перезапуск, откат и восстановление БД не выполняются вслепую.

**Демонстрация.** Открыть раздел диагностики runbook, выполнить только публичные GET-проверки и показать Events Render без секретов. Не перезапускать приложение ради ответа.

**Типичная ошибка.** Ошибка: первым действием удалить БД, выполнить seed или развернуть непроверенный коммит.

### L12-A01 Почему выбраны Render и Neon

Авторский учебный вопрос из прежнего сборника

**Полный ответ.** Методичка разрешает VPS или бесплатный облачный тариф. В выбранной архитектуре Render запускает приложение и отдает React, Neon сохраняет PostgreSQL независимо от временного диска приложения. TLS завершается инфраструктурой Render. SSH, firewall и certbot VPS-варианта здесь не настраивались вручную; это ограничение отражается в матрице, а не заменяется вымышленными командами.

**Реализация.** Render-образ собирает frontend и backend, docker/render-entrypoint.sh применяет миграции и запускает приложение. Runbook находится в docs/deployment.md.

**Краткий ответ.** Облачный тариф допускается методичкой. Render обслуживает приложение, Neon хранит базу. Ручная настройка VPS при таком размещении не заявляется.

**Демонстрация.** Открыть публичный /books и /health, затем настройки сервиса без секретов. Сверить SHA деплоя с утвержденной версией.

**Типичная ошибка.** Ошибка: описать SSH, certbot или собственный Nginx на Render как фактически выполненные действия.

### L12-A03 Почему pg_dump17 был заменен

**Краткий ответ.** Клиент 17 отказался выгружать сервер 18.6. Использован совместимый клиент 18.6. Отказ не выдавался за готовую резервную копию.

**Типичная ошибка.** Ошибка: игнорировать код возврата pg_dump и проверять только существование файла.

## Дополнительные авторские вопросы

### L7-X01 Зачем response_model, если функция уже возвращает словарь?

response_model задает публичный контракт, проверяет форму ответа и ограничивает набор возвращаемых полей. Аннотация произвольного словаря не обеспечивает ту же фильтрацию. В BookNest BookRead и UserRead отделяют публичные сведения от служебных данных; пароль и хеш не должны попадать в ответ. Схема не заменяет правильный запрос к БД и контроль доступа.

**Краткий ответ.** Схема ответа задает разрешенные поля. Она отделяет публичные данные от внутренних. Проверка доступа при этом остается обязательной.

**Демонстрация.** Сравнить модель User и схему UserRead, затем GET /auth/me в тестовой среде без вывода токена.

### L8-X01 Как обнаруживается и устраняется N+1 в BookNest?

При ленивом чтении списка первая команда получает книги, а последующие команды отдельно получают связи каждой книги. Число запросов растет с числом строк. В book_query применены selectinload для автора и жанров. Исторические логи docs/lab8/n-plus-one-before.log и n-plus-one-after.log фиксируют 26 и 3 SELECT в своем стенде. Позднее измерение 41 и 3 относится к другому контролируемому набору; смешивать их нельзя.

**Краткий ответ.** N+1 выявляется по растущему числу SQL-запросов. Связи загружаются пакетно через selectinload. В сохраненном историческом примере число SELECT уменьшилось с 26 до 3.

**Демонстрация.** Показать оба исторических лога, одинаковый сценарий и book_query. Не включать echo с пользовательскими данными на production.

### L9-X01 Почему пароль хешируется, а не просто кодируется в Base64?

Base64 является обратимым представлением и не защищает пароль. bcrypt использует соль и вычислительную стоимость, замедляя перебор после утечки хешей. При входе пароль проверяется относительно сохраненного хеша без восстановления исходного пароля. В коде применяется passlib CryptContext; секреты, пароли и хеши не включаются в UserRead, журналы или скриншоты.

**Краткий ответ.** Base64 легко декодируется. bcrypt хранит соленый хеш с настраиваемой стоимостью. При входе проверяется соответствие введенного пароля хешу.

**Демонстрация.** Открыть hash_password и verify_password, затем показать тест входа. Не показывать содержимое таблицы password_hash.

### L10-X01 Как пользователь получает понятную ошибку вместо внутреннего исключения?

Сервер возвращает общий конверт code, message, details, request_id. Клиент apiFetch преобразует неуспешный ответ в ApiError, а toUserMessage выбирает текст для пользователя. Ошибки полей можно привязать к форме; сетевой сбой и отмену запроса различают. Успех операции не показывается до подтверждения, а отрицательный сценарий проверяется тестом.

**Краткий ответ.** Сервер возвращает единый формат ошибки. Клиент переводит его в понятное сообщение. Технические подробности остаются в серверном журнале.

**Демонстрация.** Показать обработку 422 в тестовой форме и общий конверт с request_id, скрыв личные данные.

### L11-X01 Почему прямая ссылка React должна работать после перезагрузки страницы?

При переходе внутри React маршрут обрабатывает браузер, но при перезагрузке полный URL получает сервер. Для неизвестного серверу клиентского маршрута требуется вернуть index.html, чтобы React Router выбрал страницу. Для API и отсутствующих статических файлов нужен настоящий ответ ошибки, иначе JSON-запрос получит HTML. В Nginx используется try_files, в Render предусмотрен отдельный SPA fallback.

**Краткий ответ.** После перезагрузки URL сначала получает сервер. Он возвращает оболочку SPA для клиентского маршрута. Запрос API при этом должен сохранить свой код и JSON.

**Демонстрация.** Открыть /books по прямой ссылке и обновить страницу. Отдельно проверить несуществующий /api/v1 адрес на JSON 404.

### L12-X01 Что означает успешный /health и чего он не гарантирует?

В BookNest /health возвращает status=ok и подтверждает, что отвечает процесс сервера; запрос к БД в нем не выполняется. Ответ 200 не является доказательством корректности всех пользовательских сценариев, доступности внешнего Open Library или возможности восстановления копии. Поэтому runbook дополняет healthcheck проверками каталога, авторизации, журналов и БД. Сохраненная внешняя проверка также не заменяет длительную историю uptime.

**Краткий ответ.** Проверка здоровья покрывает ограниченный набор условий. Она не заменяет полный пользовательский сценарий. При сбое проверяются также журналы и зависимые сервисы.

**Демонстрация.** Открыть обработчик /health и сравнить его обязанности со списком приемки в docs/deployment.md.
