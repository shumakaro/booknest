## Цель и основные понятия

В лекции рассматриваются вложенные маршруты, layout и Outlet, параметры пути, состояние URL, формы, схемная валидация, полевые ошибки и границы ответственности клиента.
Цель состоит в том, чтобы объяснить, как путь приводит к странице, как данные проходят от формы к API и какие проверки выполняются на каждом уровне.

## Сквозной путь запроса

При прямом открытии /loans браузер разрешает имя сервиса, устанавливает HTTPS-соединение и получает HTML оболочки SPA. На Render оболочку возвращает app/render.py; в Compose эту роль выполняет Nginx. React Router выбирает страницу, RequireAuth проверяет состояние сеанса, LoansPage читает фильтр URL и вызывает apiFetch. Запрос /api/v1/loans получает FastAPI, который проверяет токен и владельца и обращается через репозиторий к PostgreSQL. JSON возвращается клиенту и обновляет интерфейс. Это описание архитектуры, а не новый полный production-прогон.
Статическая страница отдает готовое содержимое без клиентской маршрутизации, SPA выбирает экран на клиенте, SSR формирует HTML экрана на сервере. BookNest использует SPA; наличие FastAPI за тем же адресом не превращает его в SSR.

## Разбор практических примеров

Ссылка на каталог сохраняет q/page и фильтры. Личная страница /loans сохраняет state/page и получает записи, разрешенные текущему пользователю. Копирование URL не дает доступ к чужим выдачам.
Форма книги имеет два режима. Она сохраняет ошибочный ввод, связывает серверную ошибку с полем и блокирует повтор запроса. Полная форма выдачи из учебного примера относится к отдельной доработке практики 8.

## Контрольные вопросы и ответы

### Вопрос 1

Почему в SPA нельзя переходить по &lt;a href&gt; и что делает &lt;Link&gt;?

**Полный ответ.** Обычная ссылка a выполняет стандартную навигацию браузера и может загрузить документ заново. Для внутренних экранов SPA Link передает переход клиентскому роутеру: меняется адрес и отображаемая страница. Это сохраняет оболочку приложения. Запрет в вопросе относится к внутренним переходам: обычная ссылка остается уместной для внешнего сайта, скачивания или намеренной полной загрузки. При прямом открытии URL сервер все равно должен вернуть оболочку SPA.

**BookNest.** В NotFoundPage переход назад реализован Link to=/books. AppLayout использует NavLink и отмечает активный раздел. Раздача прямых ссылок в Compose и Render настроена отдельно от React Router.

**Код.** [react-app/src/pages/not-found/NotFoundPage.tsx:3](../../react-app/src/pages/not-found/NotFoundPage.tsx#L3); [react-app/src/shared/layout/AppLayout.tsx:24](../../react-app/src/shared/layout/AppLayout.tsx#L24)

**Краткий ответ.** Внутренние переходы выполняются через Link. Обычный a может перезагрузить документ. Для внешних ссылок обычный a допустим.

**Демонстрация.** Открыть неизвестный путь, нажать «Вернуться в каталог» и проверить /books. Прямую перезагрузку проверять отдельно: компонентный тест не подтверждает конфигурацию публичного сервера.

**Документация.** [React Router 7.18.4 Navigating](https://reactrouter.com/7.18.4/start/declarative/navigating)

### Вопрос 2

Как реализуется общий layout для группы маршрутов?

**Полный ответ.** Общий макет становится родительским элементом группы маршрутов. В нем размещаются постоянные части интерфейса, а Outlet задает место дочерней страницы. При переходе между дочерними URL оболочка сохраняется, а содержимое Outlet меняется. Вложенная проверка доступа может иметь свой Outlet, пропуская только разрешенные дочерние маршруты.

**BookNest.** AppRouter оборачивает страницы родительским Route с AppLayout. В AppLayout остаются навигация и уведомления. Внутри этой группы RequireAuth отдельно ограничивает личные страницы и действия библиотекаря.

**Код.** [react-app/src/app/router/AppRouter.tsx:65](../../react-app/src/app/router/AppRouter.tsx#L65); [react-app/src/shared/layout/AppLayout.tsx:24](../../react-app/src/shared/layout/AppLayout.tsx#L24)

**Краткий ответ.** Макет является родителем маршрутов. Дочерняя страница выводится в Outlet. Шапка и навигация остаются общими.

**Демонстрация.** Перейти из каталога на 404 и обратно. Показать общий AppLayout и место Outlet в исходнике.

**Документация.** [React Router 7.18.4 Routing](https://reactrouter.com/7.18.4/start/declarative/routing)

### Вопрос 3

Какое состояние следует держать в URL, а какое — в компоненте? Приведите по два примера.

**Полный ответ.** В URL помещается состояние, которое должно восстановиться по ссылке: поисковый запрос и номер страницы являются двумя примерами. В компоненте можно хранить локальное временное состояние: раскрытие меню и индикатор отправки. Критерий выбора состоит в том, должна ли другая вкладка открыть тот же результат. Смена фильтра обычно сбрасывает страницу, а неверные параметры нормализуются перед запросом.

**BookNest.** BooksPage читает q, sort, genre, available и page через useSearchParams и catalogFilters. LoansPage хранит state и page в URL. Состояния loading и pending остаются локальными и не превращаются в параметры ссылки.

**Код.** [react-app/src/pages/books/BooksPage.tsx:17](../../react-app/src/pages/books/BooksPage.tsx#L17); [react-app/src/pages/loans/LoansPage.tsx:16](../../react-app/src/pages/loans/LoansPage.tsx#L16)

**Краткий ответ.** Поиск и страница сохраняются в URL. Открытое меню и отправка остаются внутри компонента. Тогда скопированная ссылка восстанавливает существенное состояние.

**Демонстрация.** Использовать /loans?state=returned&page=2 в тестовой сессии и проверить выбранный фильтр. Другой пользователь увидит свои записи: одинаковый URL не отменяет серверную проверку владельца.

**Документация.** [React Router 7.18.4 URL Values](https://reactrouter.com/7.18.4/start/declarative/url-values)

### Вопрос 4

Что вернёт useParams() для маршрута /books/:bookId при переходе на /books/42?

**Полный ответ.** Для выбранного маршрута результат содержит bookId со строковым значением '42'. useParams не преобразует его в число и не подтверждает наличие книги. В BookNest строковый ID передается API-адаптеру и кодируется как сегмент URL. На стороне FastAPI числовой параметр проверяется отдельно. Неверный формат и отсутствующая запись являются разными случаями: валидация и 404.

**BookNest.** BookFormPage получает bookId из useParams и по его наличию выбирает режим. getBookDetailsById принимает string. Новый RoutingAcceptance.test проверяет настоящий AppRouter на /books/42 и передачу строкового ID странице деталей.

**Код.** [react-app/src/pages/books/BookFormPage.tsx:14](../../react-app/src/pages/books/BookFormPage.tsx#L14); [react-app/src/api/books.ts:20](../../react-app/src/api/books.ts#L20)

**Краткий ответ.** bookId будет строкой '42'. Роутер не проверяет существование записи. Тип и наличие ресурса проверяются следующими слоями.

**Демонстрация.** Открыть тест прямой ссылки, затем BookFormPage и API-адаптер. Не утверждать, что запись 42 существует в production.

### Вопрос 5

Зачем нужны три уровня валидации и что произойдёт при отказе от серверного?

**Полный ответ.** HTML-ограничения дают простую браузерную проверку, схема Zod проверяет форму и межполевые правила до запроса, а сервер проверяет данные независимо от клиента. Первые два уровня улучшают обратную связь; серверный уровень обязателен, поскольку запрос можно отправить напрямую. В BookNest нативные required/type=email применяются в форме входа. У BookForm задан noValidate: всплывающая проверка браузера отключена, сообщения ведет Zod. Поэтому нельзя утверждать, что все три механизма одновременно блокируют отправку именно этой формы.

**BookNest.** bookSchema проверяет поля и соотношение годов. saveBook отправляет значения, а Pydantic и CatalogService заново проверяют их. Серверный PATCH проверяет итоговую запись после объединения со старыми полями, а не доверяет dirtyFields клиента.

**Код.** [react-app/src/features/books/bookSchema.ts:4](../../react-app/src/features/books/bookSchema.ts#L4); [react-app/src/features/books/components/BookForm.tsx:39](../../react-app/src/features/books/components/BookForm.tsx#L39); [app/services/catalog.py:31](../../app/services/catalog.py#L31)

**Краткий ответ.** HTML и Zod помогают пользователю исправить ввод. Сервер повторяет проверку независимо от браузера. У формы книги noValidate оставляет клиентские сообщения под управлением Zod.

**Демонстрация.** Сравнить нативные атрибуты LoginPage и noValidate BookForm. Показать тест, где невалидная форма не вызывает saveBook, и серверную схему.

**Документация.** [MDN Client-side form validation](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Form_validation), [Zod Basic usage](https://zod.dev/basics)

### Вопрос 6

Как отобразить ошибку 422 от сервера на конкретном поле формы?

**Полный ответ.** Ответ 422 разбирается по пути поля в loc и сообщению msg. Последний сегмент пути сопоставляется с именем поля интерфейса, после чего setError добавляет сообщение. Неизвестная ошибка должна остаться общей ошибкой формы, а введенные данные сохраняются. Учебный пример ожидает исходный detail; текущий BookNest возвращает единый details. Эти форматы нельзя механически смешивать.

**BookNest.** readError получает массив body.details. saveBook переводит year в publicationYear, edition_year в editionYear, author_id в author и total_copies в totalCopies. BookForm вызывает setError для известных полей и переносит фокус; 409 ISBN показывается у isbn. Тесты проверяют и неизвестную ошибку без потери введенного.

**Код.** [react-app/src/api/bookForm.ts:19](../../react-app/src/api/bookForm.ts#L19); [react-app/src/features/books/components/BookForm.tsx:39](../../react-app/src/features/books/components/BookForm.tsx#L39); [react-app/src/api/client.ts:26](../../react-app/src/api/client.ts#L26)

**Краткий ответ.** Путь ошибки сервера переводится в имя поля формы. Сообщение передается через setError. Если поле неизвестно, показывается общая ошибка без потери ввода.

**Демонстрация.** Открыть BookFormApi.test.ts и BookForm.test.tsx. Для визуального кадра использовать тестовый ответ, не повреждая рабочие записи.

### Вопрос 7

Чем контролируемый ввод отличается от неконтролируемого и почему react-hook-form экономит перерисовки?

**Полный ответ.** При контролируемом вводе значение задается React-состоянием, а onChange обновляет его. При неконтролируемом вводе текущее значение хранит DOM. React Hook Form может регистрировать обычные поля через ref и подписывать компоненты на нужные части состояния формы. Поэтому не требуется отдельно менять родительский useState на каждый символ. Controller используется для компонентов, которым нужен контролируемый интерфейс. Число перерисовок зависит от подписок: без измерения нельзя обещать отсутствие всех перерисовок.

**BookNest.** BookForm применяет register и useForm, а тип BookFormValues выводится из bookSchema. Отдельные useState используются для общей ошибки и сохранения, а не для значения каждого текстового поля. Явный mode не указан, поэтому начальная проверка идет в стандартном режиме onSubmit, а не onBlur.

**Код.** [react-app/src/features/books/components/BookForm.tsx:39](../../react-app/src/features/books/components/BookForm.tsx#L39); [react-app/src/features/books/bookSchema.ts:74](../../react-app/src/features/books/bookSchema.ts#L74)

**Краткий ответ.** Контролируемое значение хранится в React-состоянии. Неконтролируемое значение хранит DOM. React Hook Form позволяет не обновлять родителя вручную на каждый символ.

**Демонстрация.** Показать register и отсутствие useState для каждого поля. Требование onBlur и полную форму выдачи оставить в перечне практики 8.

**Документация.** [React Hook Form useForm](https://react-hook-form.com/docs/useform), [Zod Basic usage](https://zod.dev/basics)

### Вопрос 8

Как защитить форму от двойной отправки?

**Полный ответ.** На время запроса блокируются отправка и редактирование полей, а пользователь видит состояние ожидания. Дополнительный синхронный флаг защищает от второго события до обновления React-состояния. После завершения запроса блокировка снимается в finally. На сервере остаются собственные ограничения и транзакции: выключенная кнопка не обеспечивает уникальность или однократность всех сетевых запросов.

**BookNest.** BookForm объединяет saving и isSubmitting в busy. Fieldset disabled блокирует вложенную кнопку, а lock.current не допускает повторного saveBook. Тест незавершенного Promise проверяет отключение поля и кнопки и ровно один вызов сохранения.

**Код.** [react-app/src/features/books/components/BookForm.tsx:39](../../react-app/src/features/books/components/BookForm.tsx#L39); [react-app/src/tests/BookForm.test.tsx:47](../../react-app/src/tests/BookForm.test.tsx#L47)

**Краткий ответ.** Во время запроса кнопка и поля блокируются. Синхронный lock закрывает окно до перерисовки. Сервер все равно проверяет свои ограничения.

**Демонстрация.** Показать тест с незавершенным Promise и его проверку вызовов. Не отправлять повторные POST в production ради демонстрации.

### Вопрос 9

Что такое защищённый маршрут и почему он не является мерой безопасности?

**Полный ответ.** Защищенный маршрут решает, какой интерфейс показать при текущем состоянии сеанса. Гость направляется ко входу, а роль может ограничить форму библиотекаря. Однако пользователь может обойти интерфейс и отправить HTTP-запрос напрямую. Поэтому сервер проверяет токен, роль и владельца ресурса независимо от React. Ожидание восстановления сеанса также отделяется от состояния гостя.

**BookNest.** RequireAuth показывает Spinner при loading, сохраняет location в state.from для гостя и выводит отказ при неподходящей роли. Сервер использует get_current_user, require_role и get_own_loan. Новые тесты AppRouter проверяют прямое открытие /books/new гостем и читателем.

**Код.** [react-app/src/app/router/RequireAuth.tsx:5](../../react-app/src/app/router/RequireAuth.tsx#L5); [app/core/auth.py:45](../../app/core/auth.py#L45)

**Краткий ответ.** RequireAuth управляет доступными экранами. Сервер не доверяет результату этой проверки. Токен, роль и владелец проверяются на backend независимо.

**Демонстрация.** Показать два теста прямого открытия формы. Серверные 401/403/404 подтверждать отдельными API-тестами, а не наличием скрытой кнопки.

### Вопрос 10

Сформулируйте правило зависимостей между слоями вашего проекта.

**Полный ответ.** Правило курса задает направление pages → features → shared → api и запрещает обратный импорт shared → features. app собирает роутер и провайдеры; pages связывают сценарии, features содержат предметное поведение, а shared должен оставаться общим. В проекте сохранились также components и lib. Текущая структура не полностью следует строгой схеме: AppLayout в shared импортирует RouteAccessibility из features и useAuth/useTheme из app. Такой макет фактически зависит от приложения; это технический долг, а не пример чистого shared.

**BookNest.** Разделение HTTP и интерфейса уже есть: сетевые вызовы размещены в api, правила формы в bookSchema, экран собирается в BookFormPage. Для дальнейшей очистки AppLayout следует рассматривать как композицию app, сохраняя поведение и исторические ветки. Автоматического запрета обратных импортов в ESLint сейчас нет, поэтому успешный lint не доказывает соблюдение всей архитектуры.

**Код.** [react-app/src/shared/layout/AppLayout.tsx:24](../../react-app/src/shared/layout/AppLayout.tsx#L24); [react-app/src/pages/books/BookFormPage.tsx:14](../../react-app/src/pages/books/BookFormPage.tsx#L14); [react-app/src/api/bookForm.ts:19](../../react-app/src/api/bookForm.ts#L19)

**Краткий ответ.** Страницы связывают сценарии, features содержат функции, shared содержит общее. Обратные зависимости следует ограничивать. В текущем макете есть конкретный долг, который обозначен явно.

**Демонстрация.** Открыть импорты AppLayout и показать фактическое направление. Не представлять схему каталогов как доказательство отсутствия обратных зависимостей.

## Результаты и ограничения

Ответы сверены с текущими исходниками. Добавлены четыре интеграционные проверки настоящего AppRouter: 404 и возврат, динамический ID, перенаправление гостя, отказ роли читателю.
Результаты Vitest, ESLint и сборки записываются в отдельном протоколе после завершения команд. Старый успешный CI не заменяет новый запуск.
- Форма книги не заменяет требуемую в практике 8 форму выдачи с двумя датами.
- Защита несохраненных данных через confirm не закрывает все переходы history.
- Макет в shared имеет обратные зависимости; это отмеченный технический долг.
- Браузерная ручная приемка и личная демонстрация компетенций еще не выполнены.
