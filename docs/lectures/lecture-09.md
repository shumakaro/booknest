## Вопрос 1

Чем ASGI отличается от WSGI и зачем нужен Uvicorn?

**Полный ответ.** WSGI задает синхронный интерфейс сервер–приложение для HTTP. ASGI описывает обмен событиями через scope, receive и send и поддерживает, в частности, HTTP и WebSocket. Uvicorn является ASGI-сервером: принимает сетевой запрос и вызывает FastAPI. Он не заменяет сам фреймворк. Асинхронный интерфейс не превращает синхронный драйвер БД в неблокирующий.

**BookNest.** Приложение собирается create_app в app/main.py. Учебная версия с памятью отдельно находится в app/legacy.py и не подменяет действующий SQLAlchemy API. В этом блоке TestClient вызывает приложения в процессе: запуск отдельного Uvicorn и публичное развертывание не заявляются.

**Код.** [app/main.py:17](../../app/main.py#L17); [app/legacy.py:13](../../app/legacy.py#L13)

**Краткий ответ.** ASGI передает события и допускает асинхронную работу. WSGI использует синхронный интерфейс. Uvicorn запускает FastAPI как ASGI-приложение.

**Демонстрация.** Показать две фабрики приложения и их разные зависимости. Не называть TestClient отдельным запущенным сервером.

**Документация.** [ASGI: Introduction](https://asgi.readthedocs.io/en/latest/introduction.html), [FastAPI: Concurrency and async](https://fastapi.tiangolo.com/async/)

## Вопрос 2

Как должен выглядеть URL и метод для операций «получить все книги», «создать книгу», «выдать книгу №42»?

**Полный ответ.** Получение списка — GET /api/v1/books, создание — POST /api/v1/books с телом BookCreate. Выдача книги №42 — POST /api/v1/books/42/loans с телом LoanCreate. URL обозначает ресурс, а действие задается HTTP-методом. Сервер возвращает идентификатор созданной выдачи; это другой идентификатор, чем номер книги.

**BookNest.** LoanCreate содержит due_date и необязательный user_id. Читатель оформляет выдачу себе; библиотекарь может выбрать другого читателя. Возврат выполняется PATCH /api/v1/loans/{loan_id} с состоянием returned, поэтому подставлять book_id вместо loan_id нельзя. Тестовый пример с №42 не является существующей production-записью.

**Код.** [app/routers/catalog_db.py:44](../../app/routers/catalog_db.py#L44); [app/routers/loans.py:17](../../app/routers/loans.py#L17)

**Краткий ответ.** GET читает список, POST создает книгу. Выдача — отдельный ресурс loans внутри книги. Для возврата нужен ID выдачи.

**Демонстрация.** В спецификации найти эти три операции. Создание и выдачу выполнять только на своей тестовой записи при отдельной ручной приемке.

## Вопрос 3

Когда возвращается 201, 204, 400, 404, 409, 422?

**Полный ответ.** 201 означает создание ресурса; 204 — успешное действие без тела ответа. 400 обозначает некорректный запрос, 404 — отсутствие доступного ресурса, 409 — конфликт с текущими данными, 422 — нарушение схемы или правил входных полей. Пустой список остается успешным ответом 200. Отдельно 401 означает необходимость действующей аутентификации, 403 — недостаточное разрешение.

**BookNest.** В памяти проверены создание 201, повтор ISBN 409, неизвестный ID 404, неверный год 422 и удаление 204 с пустым телом. В текущем API чужая выдача скрывается за 404. Ошибка типа параметра дает 422, а не 404. Код 400 указан в общих ответах; CORS может вернуть собственный текстовый 400 для неверного preflight — его нельзя выдавать за JSON-ошибку каталога.

**Код.** [app/core/http.py:16](../../app/core/http.py#L16); [app/core/auth.py:45](../../app/core/auth.py#L45); [tools/check_lecture09_contracts.py:124](../../tools/check_lecture09_contracts.py#L124)

**Краткий ответ.** 201 — создано; 204 — выполнено без тела. 404 — не найдено, 409 — конфликт. 422 показывает ошибку входных данных.

**Демонстрация.** Открыть memory_http_cases и показать фактические коды и пустой DELETE. Не приписывать этому прогону проверки настоящих выдач в PostgreSQL.

**Документация.** [FastAPI: Handling Errors](https://fastapi.tiangolo.com/tutorial/handling-errors/)

## Вопрос 4

Зачем разделять схемы Create, Update и Read? Приведите поле, которое есть только в одной из них.

**Полный ответ.** Create описывает допустимые поля создания, Update — изменения, Read — публичный результат. Это не позволяет клиенту самостоятельно задавать серверные поля и помогает скрывать служебные данные. Например, id книги присутствует в BookRead, но не в BookCreate. Пропуск поля Update и явный null имеют разный смысл: разрешение очистки зависит от конкретного поля.

**BookNest.** BookCreate задает обязательные поля, BookUpdate допускает их пропуск, а BookRead добавляет id, author, available и внешние идентификаторы. Для пользователей пароль принимается RegisterRequest, но не выдается через UserRead. В PATCH ISBN можно очистить, а обязательное название нельзя превратить в null.

**Код.** [app/schemas/__init__.py:77](../../app/schemas/__init__.py#L77); [app/schemas/__init__.py:136](../../app/schemas/__init__.py#L136); [app/schemas/__init__.py:179](../../app/schemas/__init__.py#L179); [app/schemas/auth.py:7](../../app/schemas/auth.py#L7)

**Краткий ответ.** Create принимает данные новой записи. Update различает пропуск и изменение. Read содержит только разрешенные поля ответа, включая серверный id.

**Демонстрация.** Сравнить model_fields трех схем и nullable/required в OpenAPI; не отправлять настоящие пароли в протокол.

**Документация.** [FastAPI: Response Model](https://fastapi.tiangolo.com/tutorial/response-model/), [FastAPI: Body Updates](https://fastapi.tiangolo.com/tutorial/body-updates/)

## Вопрос 5

Что делает response_model и какую уязвимость предотвращает?

**Полный ответ.** response_model описывает схему ответа, участвует в его проверке, сериализации и фильтрации и попадает в OpenAPI. Отдельная публичная схема помогает предотвратить избыточную выдачу данных, например password_hash. Это не заменяет проверку токена, роли или владельца: разрешенный набор полей и разрешение доступа являются разными проверками.

**BookNest.** Маршрут /auth/me использует UserRead, который не содержит password_hash. Локальная проверка передала фиктивный служебный ключ в UserRead и убедилась, что его нет в model_dump. Это проверка схемы, а не новый HTTP-запрос /me с настоящим пользователем. Каталог также возвращает BookRead вместо произвольного ORM-объекта.

**Код.** [app/routers/auth.py:94](../../app/routers/auth.py#L94); [app/schemas/auth.py:27](../../app/schemas/auth.py#L27); [tools/check_lecture09_contracts.py:129](../../tools/check_lecture09_contracts.py#L129)

**Краткий ответ.** response_model ограничивает и проверяет выходные поля. Это защищает от случайной утечки служебных данных. Права доступа сервер проверяет отдельно.

**Демонстрация.** Показать response_model=UserRead и безопасную проверку с фиктивным полем в протоколе.

**Документация.** [FastAPI: Response Model](https://fastapi.tiangolo.com/tutorial/response-model/)

## Вопрос 6

Как Pydantic сообщает клиенту об ошибке валидации и как выглядит структура ответа?

**Полный ответ.** Pydantic формирует сведения о нарушениях схемы, а FastAPI преобразует ошибки входного запроса в HTTP 422. Стандартный формат FastAPI использует detail со списком ошибок. В BookNest обработчик намеренно заменяет его единым конвертом code, message, details и request_id. Каждый элемент details содержит loc, msg и type. Ошибка выходной модели является серверной проблемой, а не ошибкой пользователя 422.

**BookNest.** validation_error исключает input и ctx, чтобы не вернуть пароль или другое присланное значение. HTTP-протокол подтвердил 422 для year="давно" и точный набор полей конверта. loc указывает участок запроса и поле. Зависимости могут исполняться до обработчика маршрута, поэтому нельзя строить безопасность на предположении, что неверное тело вообще не вызовет зависимостей.

**Код.** [app/core/http.py:101](../../app/core/http.py#L101); [app/schemas/__init__.py:199](../../app/schemas/__init__.py#L199)

**Краткий ответ.** Неверный вход дает 422. В нашем проекте ошибки полей лежат в details. Исходное значение поля обратно не возвращается.

**Демонстрация.** Найти реальный 422 в протоколе и сравнить его с ErrorRead в Swagger.

**Документация.** [FastAPI: Handling Errors](https://fastapi.tiangolo.com/tutorial/handling-errors/)

## Вопрос 7

Для чего нужен механизм Depends? Приведите два применения.

**Полный ответ.** Depends объявляет, что обработчику нужен результат другой функции. FastAPI разрешает цепочку зависимостей и передает результат в параметр, а yield-зависимость может освободить ресурс после обработки. Два применения: получение сессии БД и проверка текущего пользователя. Проверку роли можно построить поверх зависимости пользователя.

**BookNest.** Database передает Session, CurrentUser проверяет токен, Librarian добавляет ограничение роли. Pagination переиспользует ограничения page и size. В тестах dependency_overrides подменяет внешнего клиента; это управляемая тестовая подмена, а не отключение production-защиты. В безопасном прогоне любые Engine.connect запрещены дополнительно.

**Код.** [app/core/auth.py:15](../../app/core/auth.py#L15); [app/core/auth.py:30](../../app/core/auth.py#L30); [app/core/pagination.py:6](../../app/core/pagination.py#L6)

**Краткий ответ.** Depends собирает необходимые обработчику значения. В BookNest это сессия БД и текущий пользователь. Проверку роли тоже можно оформить зависимостью.

**Демонстрация.** Открыть цепочку CurrentUser → get_current_user и Librarian → require_role.

## Вопрос 8

Чем PATCH отличается от PUT и что делает exclude_unset=True?

**Полный ответ.** PUT обычно задает полное новое представление ресурса, PATCH — только указанные изменения. model_dump(exclude_unset=True) исключает поля, которые клиент не передал, но сохраняет явно переданные null или значения, совпадающие с умолчанием. Это не равно exclude_none. Допустимость null все равно проверяет схема. Сам model_copy(update=...) не заменяет полную валидацию итогового состояния.

**BookNest.** Рабочий каталог использует PATCH. CatalogService.save объединяет изменения с сохраненными полями и повторно проверяет BookCreate: так год выпуска и год издания не конфликтуют после частичного обновления. В памяти PATCH только названия сохранил остальные поля. Единственный DB-тест null-правил намеренно не вошел в этот прогон; проверка реального SQL-обновления здесь не заявляется.

**Код.** [app/routers/catalog_db.py:81](../../app/routers/catalog_db.py#L81); [app/services/catalog.py:39](../../app/services/catalog.py#L39)

**Краткий ответ.** PATCH изменяет переданные поля. exclude_unset оставляет именно их. Затем нужно проверить допустимость получившейся записи.

**Демонстрация.** Показать model_dump(exclude_unset=True), объединение и BookCreate.model_validate; сравнить HTTP-ответ до и после изменения названия.

**Документация.** [FastAPI: Body Updates](https://fastapi.tiangolo.com/tutorial/body-updates/)

## Вопрос 10

Почему нельзя выполнять блокирующий код внутри async def?

**Полный ответ.** Блокирующий вызов внутри async def занимает поток цикла событий и задерживает другие задачи в этом процессе. await дает возможность переключаться только для действительно асинхронной операции. Синхронные обработчики и зависимости def FastAPI обычно выполняет через пул потоков. Обычный helper, вызванный напрямую внутри async def, автоматически туда не переносится. Для тяжелой CPU-работы обычно нужен отдельный процесс или очередь.

**BookNest.** Рабочие маршруты с синхронным SQLAlchemy объявлены def. Open Library также вызывается синхронным обработчиком def через httpx; это не async-драйвер. Асинхронное middleware ожидает call_next. Переписывание только слова def на async def без замены ввода-вывода ухудшило бы поведение. Нагрузочный тест конкурентности в этом блоке не запускался.

**Код.** [app/routers/discover.py:32](../../app/routers/discover.py#L32); [app/core/http.py:49](../../app/core/http.py#L49)

**Краткий ответ.** Блокирующий вызов останавливает цикл событий. Для async нужен неблокирующий ввод-вывод. Синхронный маршрут можно оставить def.

**Демонстрация.** Сравнить def search_books и async middleware; объяснить, почему синхронный клиент не становится асинхронным от переименования функции.
