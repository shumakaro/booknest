# Лабораторная работа 11 Контейнеризация BookNest

## 1 Тема и цель
Подготовлен воспроизводимый запуск BookNest через Docker Compose. Цель работы — разделить сборку и выполнение, сохранить данные между пересозданиями контейнеров и автоматизировать проверки PR. Отчёт охватывает лекцию, практику и СРС недели 14; начало развёртывания рассматривается также в отчёте лабораторной 12.

## 2 Программное обеспечение
Использованы Dockerfile, Compose Specification, PostgreSQL 17 Alpine, Python 3.12 Slim, Node 24 Alpine и Nginx Stable Alpine. Локально загружен официальный автономный Docker Compose v5.7.0 только в .tools. Docker Engine отсутствует, а WSL сообщает, что подсистема не установлена. Поэтому наличие валидатора не выдаётся за наличие работающих контейнеров.

## 3 Краткая теория
По лекции 14 контейнеризация решает проблему различий окружений. Образ состоит из слоёв; порядок COPY определяет повторное использование кэша. Multi-stage отделяет сборщик от runtime. Compose задаёт сеть, переменные, зависимости и тома. Nginx обслуживает SPA и передаёт /api внутрь сети, а готовность БД проверяется healthcheck, а не только порядком старта.

## 4 Ход выполнения
Создана зависимая ветка lab-11/docker. Backend собирается отдельной стадией зависимостей, после чего в runtime копируются только production-пакеты и код. Установка выполняется без кэша и компиляции pyc; транзитивные версии ограничены requirements-lock.txt. Приложение работает от appuser. Стадия test добавляет тестовые инструменты отдельно.

Frontend собирается Node и переносит только dist в Nginx. Перед исходниками копируются package-файлы и выполняется npm ci. Созданы .dockerignore обоих контекстов; .env, .tools, .venv, Git и кэши исключены. Скрипты shell фиксируются с LF.

Основной Compose содержит четыре сервиса: db, api, seed и web. Одноразовый seed — функциональная четвёртая служба: готовит демонстрационный каталог и отсутствующие роли после готовности API. При непустом каталоге наполнение пропускается, старые пароли не меняются. PostgreSQL использует именованный pgdata; локальные демонстрационные учётные данные хранятся в отдельном томе, а не образе.

API при старте читает версию схемы и применяет только новые ревизии. Внутренний адрес БД — db, API не публикует порт на хост. Единственный внешний вход — web; по умолчанию он привязан к 127.0.0.1. В Nginx заданы proxy_pass, try_files, gzip и длительное кэширование хешированных ассетов.

## 5 Объяснение файлов
Dockerfile backend находится в docker/api.Dockerfile. docker/entrypoint.sh отличает обычный запуск от явно переданной команды seed/test; перед сервером запускается безопасное обновление схемы. requirements-runtime.txt исключает тестовые инструменты, но использует общий lock как constraints.

react-app/Dockerfile задаёт Node → Nginx, nginx.conf обслуживает /api, /health, ассеты и прямые SPA-ссылки. docker-compose.yml описывает сервисы, тома, healthcheck, restart и ротацию журналов. docker-compose.dev.yml подключается только явно и добавляет hot reload.

.github/workflows/ci.yml запускает backend/клиентские проверки и отдельный контейнерный сценарий на чистом runner. .github/workflows/images.yml публикует runtime-образы в GHCR только при теге v*. Секреты берутся из окружения и штатного токена GitHub; статических ключей в YAML нет.

## 11 Контрольные вопросы лекции 14
### Лекция 14
### Чем контейнер отличается от виртуальной машины?
Контейнер запускает изолированные процессы с использованием ядра хоста; виртуальная машина включает отдельную гостевую ОС и ядро. Поэтому контейнер обычно легче и быстрее запускается. Linux-контейнеры на Windows всё равно требуют совместимой среды, часто виртуальной машины через WSL2.

### Почему COPY requirements.txt должен идти до COPY .?
Сначала копируется редко меняющийся список зависимостей и выполняется установка, затем исходный код. Тогда правка Python-файла не отменяет кэш слоя установки пакетов. Если сначала выполнить COPY . ., любое изменение проекта заставит пересобрать все последующие слои.

### Что даёт multi-stage сборка и на сколько уменьшает образ клиента?
Multi-stage оставляет в конечном образе только результат сборки и необходимые runtime-файлы. Node, компилятор и node_modules сборщика не переходят в Nginx-образ. Лекция приводит пример примерно 1,2 ГБ → 50 МБ; собственный размер нужно измерить docker images, а не выдавать пример лекции за результат проекта.

### Как сервис api находит базу данных внутри compose-сети?
Compose создаёт сеть и внутренний DNS по именам сервисов. Поэтому адрес БД для api — db:5432, а localhost внутри api указывает на сам контейнер. Публикация порта БД на хост для общения сервисов не требуется.

### Зачем нужен том и что произойдёт при docker compose down -v?
Именованный том хранит данные независимо от жизненного цикла контейнера. Обычный down удаляет контейнеры и сеть, но сохраняет том; down -v удаляет и связанные тома, что уничтожает данные. На существующем проекте такая команда не выполняется без явного разрешения и необходимой резервной копии.

### Для чего нужен healthcheck и почему depends_on без него недостаточен?
Healthcheck проверяет готовность сервиса, например ответ pg_isready. Обычный depends_on задаёт порядок запуска контейнеров, но не означает готовность PostgreSQL принимать подключения. condition: service_healthy заставляет API дождаться успешной проверки.

### Объясните строку try_files $uri $uri/ /index.html.
Nginx сначала ищет файл по $uri, затем каталог по $uri/. Если ничего нет, отдаётся /index.html, после чего маршрут обрабатывает React Router. Это позволяет открыть /books/42 напрямую; для отсутствующего API-маршрута должен сохраняться серверный 404, а не HTML SPA.

### Что делает reverse proxy и почему API не публикуют напрямую?
Reverse proxy принимает внешний запрос и передаёт API на внутренний сервис. Это даёт единую точку TLS, ограничений, заголовков и журналов. Если API опубликован напрямую, часть этих правил можно обойти; поэтому снаружи открывается только web-вход.

### Как передать секреты в контейнер, не помещая их в образ?
Секреты передаются при запуске через окружение или механизм secrets, а не COPY и не Dockerfile ARG. Локальный .env исключается из Git и контекста сборки. Доступ к файлу сервера ограничивается; переменные клиента VITE_ для секретов не подходят.

### Как выполняется повторное развёртывание после изменений в коде и в схеме БД?
После получения нового кода собирается новая версия, проверяется резервная копия и применяются новые миграции перед стартом API. Затем проверяются health, журналы и основной сценарий. Откат приложения возможен только при совместимой схеме; удалять том для обновления нельзя.

### Что должно происходить в CI при каждом Pull Request?
При каждом PR выполняются установка зафиксированных зависимостей, линтер, backend-тесты на отдельной БД, клиентские тесты и production-сборка. Ошибка должна дать ненулевой код и красный статус. Автоматическое объединение и публикация секретов в лог недопустимы; деплой отделяется от проверки PR.


## 12 Дополнительные вопросы лабораторной
Отдельного списка нет. Почему seed выделен четвёртым сервисом? Это одноразовая задача после миграций и готовности API, а не постоянно работающий процесс; её успешное завершение служит условием запуска web. Почему нет автоматического docker-compose.override.yml? Такой файл менял бы production-запуск без явного выбора; dev-файл подключается осознанно.

## 13 Дополнительные вопросы практики
Как отличить синтаксически правильный Compose от работающего приложения? config проверяет модель, но только сборка и запуск подтверждают образы, сеть, права, миграции и HTTP. Почему нельзя показать размер до docker inspect? Размер зависит от реальных слоёв и зависимостей; пример лекции не является измерением проекта.

## 14 Выводы
BookNest подготовлен к контейнерному запуску без публикации API и БД напрямую. Разделение стадий уменьшает состав production-образов. Именованные тома сохраняют данные, а healthcheck связывает запуск с готовностью сервисов. Миграции и начальные данные встроены в последовательность запуска. Конфигурации проверены настоящим Compose, а runtime-проверки вынесены в CI из-за отсутствия местного Engine. Неполученные размеры и статусы не подменяются предположениями.
